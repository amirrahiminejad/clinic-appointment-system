## ۱. هدف

این سند سناریوهای آزمون لازم برای اعتبارسنجی User Storyهای سامانه مدیریت نوبت‌دهی کلینیک را تعریف می‌کند.

هر سناریو دارای شناسه مستقل، Story مرتبط، پیش‌شرط، اقدام، نتیجه مورد انتظار و سطح پیشنهادی آزمون است. هدف این است که تیم توسعه و تضمین کیفیت بتوانند ارتباط میان نیازمندی، معیار پذیرش و آزمون را حفظ کنند.

### اصول طراحی آزمون

- سناریوهای موفق، ناموفق، مرزی و دسترسی غیرمجاز پوشش داده شوند.
- هر آزمون نتیجه قابل مشاهده و قابل بررسی داشته باشد.
- آزمون‌های مربوط به ظرفیت و ثبت هم‌زمان، علاوه بر رابط کاربری، در سطح سرویس و پایگاه داده نیز اجرا شوند.
- خطای فنی یا نامشخص‌بودن نتیجه عملیات نباید به نمایش موفقیت کاذب منجر شود.
- رفتارهای وابسته به تصمیم‌های باز، تا زمان تعیین تکلیف با وضعیت `Blocked` مشخص شوند.
- مقادیر پیشنهادی کارایی تا زمان تأیید ذی‌نفعان، معیار قطعی انتشار محسوب نشوند.

## ۲. راهنمای وضعیت و سطح آزمون

### وضعیت آزمون

| وضعیت | معنی |
|---|---|
| `Ready` | معیار پذیرش به‌اندازه کافی روشن است و می‌توان آزمون را اجرا کرد. |
| `Blocked` | اجرای آزمون قطعی به تصمیم کسب‌وکار حل‌نشده وابسته است. |
| `Proposed` | آزمون یا آستانه پیشنهادی است و نیازمند تأیید است. |

### سطح آزمون

| سطح | کاربرد |
|---|---|
| `Unit` | اعتبارسنجی منطق مستقل و قواعد کسب‌وکار |
| `Integration` | بررسی تعامل سرویس‌ها، پایگاه داده و سرویس پیامک |
| `API` | بررسی رفتار ورودی و خروجی API |
| `E2E` | اجرای جریان کامل از دید کاربر |
| `Security` | بررسی مجوزها و حفاظت از اطلاعات |
| `Performance` | سنجش زمان پاسخ و رفتار زیر بار |

## ۱۷. معیار پیشنهادی آمادگی برای انتشار

پیش از پذیرش نسخه MVP، حداقل شرایط زیر بررسی شوند:

- [ ] تمام سناریوهای اصلی ثبت، مشاهده، تغییر و لغو نوبت با موفقیت اجرا شده‌اند.
- [ ] هیچ آزمون بحرانی مربوط به تداخل یا تجاوز از ظرفیت شکست نخورده است.
- [ ] کنترل دسترسی نقش‌ها و حفاظت از اطلاعات بیماران بررسی شده است.
- [ ] سناریوهای تغییر برنامه پزشک و حفظ نوبت‌های قبلی اعتبارسنجی شده‌اند.
- [ ] رفتار خطا و نتیجه نامشخص عملیات بررسی شده است.
- [ ] تصمیم‌های باز مسدودکننده قابلیت‌های فعال‌شده تعیین تکلیف شده‌اند.
- [ ] آزمون‌های پیامک و یادآوری مطابق سیاست نهایی محصول اجرا شده‌اند.
- [ ] معیارهای کارایی و دسترس‌پذیری موردتوافق ذی‌نفعان اندازه‌گیری شده‌اند.
- [ ] ارتباط بین PRD، User Storyها و آزمون‌ها بازبینی شده است.

## ۱۸. نکات اجرایی

- شناسه آزمون‌ها را پس از انتشار تغییر نده؛ در صورت تغییر سناریو، همان شناسه را حفظ کن مگر اینکه هدف آزمون کاملاً عوض شده باشد.
- نتیجه هر اجرای آزمون را در ابزار مدیریت تست یا گزارش CI ثبت کن؛ این فایل تعریف سناریوهاست، نه تاریخچه اجرای آن‌ها.
- برای آزمون‌های ظرفیت، تداخل زمانی و درخواست‌های هم‌زمان، فقط آزمون رابط کاربری کافی نیست.
- برای پیامک، از سرویس آزمایشی یا Mock کنترل‌شده استفاده کن تا آزمون‌ها به ارسال پیامک واقعی وابسته نباشند.
- پس از نهایی‌شدن تصمیم‌های باز، وضعیت `Blocked` را به `Ready` تغییر بده و معیار دقیق آزمون را به‌روزرسانی کن.
