# تبدیل نیازمندی‌های کیفی سامانه نوبت‌دهی کلینیک به شاخص‌های مهندسی

نکته مهم معماری این است که همه نیازمندی‌های کیفی را نباید به یک عدد دلخواه تبدیل کرد. بعضی از آن‌ها به SLO و آستانه پذیرش نیاز دارند؛ بعضی دیگر، مثل جلوگیری از دسترسی غیرمجاز یا ثبت نوبت متداخل، باید به‌صورت invariant و شرط صحت قطعی تعریف شوند.

مقادیر زیر پیشنهاد اولیه برای MVP یک کلینیک هستند، نه تعهدهای نهایی کسب‌وکار. به‌ویژه اهداف عملکردی باید با حجم واقعی استفاده، زیرساخت و تعداد کاربران اعتبارسنجی شوند. در PRD نیز هدف اولیه پاسخ‌گویی کمتر از ۲ ثانیه برای ۹۵٪ درخواست‌ها ذکر شده است.&#x20;

## ۳. امنیت، حریم خصوصی و کنترل دسترسی

در سامانه‌ای که اطلاعات هویتی بیماران را نگهداری می‌کند، معیار امنیت صرفاً «امن بودن» یا نداشتن خطای امنیتی نیست. باید مجموعه‌ای از آزمون‌های قابل تکرار و کنترل‌های قابل ممیزی تعریف شود. نیازمندی‌های NFR-001 تا NFR-004 در PRD به حفاظت از اطلاعات، محدودیت دسترسی و جلوگیری از افشای اطلاعات حساس اشاره می‌کنند.&#x20;

## ۷. شرایط پایه پیشنهادی برای آزمون کارایی MVP

برای اینکه شاخص‌ها قابل‌اندازه‌گیری و تکرارپذیر باشند، پیشنهاد می‌کنم آزمون اولیه را با این پروفایل شروع کنید. این مقادیر فرض آزمون‌اند، نه برآورد قطعی بار تولید.

| پارامتر               | مقدار پیشنهادی اولیه                                                      |
| --------------------- | ------------------------------------------------------------------------- |
| کاربران هم‌زمان       | ۲۰ کاربر                                                                  |
| تعداد بیمار           | ۱۰۰ هزار                                                                  |
| تعداد پزشک            | ۱۰۰                                                                       |
| تعداد نوبت            | یک میلیون                                                                 |
| مدت آزمون پایدار      | ۳۰ دقیقه                                                                  |
| زمان پاسخ متداول      | `p95 ≤ 2s`                                                                |
| زمان پاسخ انتهایی     | `p99 ≤ 4s`                                                                |
| صحت ظرفیت و عدم تداخل | ۱۰۰٪                                                                      |
| آزمون بازیابی         | یک سناریوی قطع سرویس و بازیابی پشتیبان                                    |
| معیار گزارش           | زمان پاسخ، نرخ خطا، throughput، مصرف CPU و حافظه، تعداد نوبت‌های ناسازگار |

این پروفایل را پس از دریافت برآورد تعداد بیماران، تعداد نوبت روزانه و تعداد کاربران پذیرش از کلینیک اصلاح کنید. همچنین بهتر است آزمون ثبت نوبت هم‌زمان را جدا از آزمون بار معمول اجرا کنید؛ چون صحت تراکنش مهم‌تر از سرعت صرف است.

## جمع‌بندی معماری

سه دسته شاخص را در اسناد نیازمندی از هم جدا نگه دارید:

- SLOهای قابل‌اندازه‌گیری: مانند `p95 ≤ 2s`، دسترس‌پذیری ماهانه و زمان بازیابی.
- Invariants قطعی: مانند صفر نوبت متداخل، صفر دسترسی غیرمجاز موفق در آزمون‌ها و عدم ایجاد نوبت تکراری بر اثر retry یک درخواست idempotent.
- اهداف نیازمند تأیید کسب‌وکار: مانند زمان دقیق بازیابی، مهلت لغو، سیاست یادآوری و نرخ قابل‌قبول خطای تشخیص بیمار تکراری.

یک نکته ظریف هم مهم است: برای دسترس‌پذیری، فقط سلامت سرور را اندازه نگیرید؛ مسیر واقعی کاربر از ورود تا ثبت نوبت باید مانیتور شود. سروری که پاسخ HTTP 200 می‌دهد ولی امکان رزرو صحیح ندارد، از دید کسب‌وکار در دسترس نیست.
