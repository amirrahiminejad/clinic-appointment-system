# نیازمندی‌های غیر عملکردی 

| شناسه      | نیازمندی غیرعملکردی                                                                                                       | معیار قابل‌اندازه‌گیری / معیار پذیرش                                                                                                                             | دسته                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| **NFR-01** | عملیات معمول سیستم باید با تأخیر پایین پاسخ داده شوند.                                                                    | پیشنهاد اولیه: **p95 ≤ 200ms** برای عملیات عادی و **p95 ≤ 300ms** برای ثبت رزرو                                                                                  | Performance                               |
| **NFR-02** | در تعارض بین سرعت و صحت، **صحت رزرو اولویت مطلق دارد**.                                                                   | ‏**Double-booking = 0**؛ هیچ رزروی نباید با وضعیت موفق اعلام شود مگر اینکه واقعاً ثبت شده باشد.                                                                  | Performance / Consistency                 |
| **NFR-03** | سیستم باید امکان رشد تعداد کاربران را بدون بازطراحی اساسی معماری فراهم کند.                                               | حدود **1000 کاربر در سال اول**؛ معماری باید امکان افزایش ظرفیت بدون بازنویسی کامل را داشته باشد.                                                                 | Scalability                               |
| **NFR-04** | افزایش ظرفیت باید تدریجی و از نظر هزینه قابل‌کنترل باشد.                                                                  | امکان **Scale-up / Scale-out تدریجی** بدون الزام به تهیه ظرفیت بسیار بیشتر از نیاز واقعی.                                                                        | Scalability / Cost                        |
| **NFR-05** | سیستم باید در ساعات کاری کلینیک قابل‌اعتماد و در دسترس باشد.                                                              | ‏Availability هدف باید به‌صورت SLA/SLO تعیین شود؛ مثلاً **99.9%** در ساعات کاری.                                                                                 | Availability                              |
| **NFR-06** | خرابی یک جزء نباید باعث ازکارافتادن کل سیستم شود؛ قابلیت‌های غیرحیاتی باید فقط قابلیتهای سیستم را کم کنند.                | تعریف سناریوهای Failure و مشخص‌کردن اینکه در خرابی هر Component چه قابلیت‌هایی باید همچنان فعال باشند.                                                           | Availability / Resilience                 |
| **NFR-07** | دسترسی به اطلاعات باید مبتنی بر Role و محدود به داده‌های مجاز هر نقش باشد.                                                | هر یک از نقشهای بیمار، پزشک، متصدی و مدیر کلینیک فقط قابلیتهایی که برای نقش آنها تعریف شده را در اختیار داشته باشند و دسترسی نقشها به هر Endpoint قابل تست باشد. | Security                                  |
| **NFR-08** | اطلاعات شخصی و حساس بیماران باید محرمانه و در برابر تغییر غیرمجاز محافظت شوند.                                            | دسترسی و تغییر اطلاعات حساس فقط برای کاربران مجاز؛ تمام مسیرهای دسترسی/تغییر حساس باید قابل کنترل و تست باشند.                                                   | Security                                  |
| **NFR-09** | قوانین کسب‌وکار مانند مهلت لغو و محدودیت نوبت فعال باید قابل تغییر باشند.                                                 | تغییر Ruleهای مشخص‌شده بدون تغییر اساسی در منطق اصلی سیستم.                                                                                                      | Maintainability / Configurability         |
| **NFR-10** | طراحی نباید توسعه آینده به چند کلینیک را مسدود کند، بدون اینکه MVP بیش‌ازحد پیچیده شود.                                   | امکان اضافه‌شدن Multi-Clinic در آینده بدون بازنویسی اساسی هسته سیستم.                                                                                            | Maintainability / Extensibility           |
| **NFR-11** | عملیات حساس باید دارای Audit Trail باشند.                                                                                 | حداقل ثبت **‏Actor، Timestamp، Operation، Before/After** برای ایجاد، لغو و تغییر نوبت.                                                                           | Auditability                              |
| **NFR-12** | کاربر جدید باید بدون آموزش قبلی بتواند نوبت بگیرد و فرآیند ساده باشد.                                                     | تعداد مراحل فرآیند رزرو باید مشخص و قابل تست باشد؛ مثلاً ≤ **X مرحله**.                                                                                          | Usability                                 |
| **NFR-13** | پس از رزرو، کاربر باید به‌صورت واضح تأییدیه نوبت شامل پزشک و زمان دریافت کند.                                             | راحتی استفاده باید شامل حداقل **Doctor + Date + Time + Booking Reference** باشد و حداکثر طی زمان مشخص انجام شوند.                                                | Usability                                 |
| **NFR-14** | در درخواست همزمان برای یک Slot، فقط یکی از کاربران باید موفق شود و سایر کاربران باید از unavailable شدن Slot مطلع شوند.   | برای هر Slot در هر زمان حداکثر **یک رزرو موفق**؛ درخواست‌های رقابتی باید نتیجه قطعی داشته باشند.                                                                 | Consistency / Usability                   |
| **NFR-15** | ‏Notification پس از رزرو موفق و همچنین لغو/تغییر نوبت باید قابل اتکا باشد و امکان افزودن کانال‌های مختلف وجود داشته باشد. | ‏Notification باید پس از Event مربوطه ایجاد شود؛ SLA تحویل باید مشخص شود. Architecture باید Channel-Agnostic باشد.                                               | Reliability / Performance / Extensibility |
| **NFR-16** | سیستم باید امکان تعریف قوانین متفاوت برای پزشکان یا کلینیک‌های مختلف را بدون Hard-code کردن منطق اصلی فراهم کند.          | ‏Ruleهای قابل تغییر باید خارج از Business Logic ثابت قابل مدیریت باشند.                                                                                          | Maintainability / Configurability         |
| **NFR-17** | عملیات رزرو باید Atomic باشد و موفقیت اعلام‌شده باید معادل ثبت قطعی رزرو باشد.                                            | ‏**Double-booking = 0**؛ پس از Success، Slot نباید به کاربر دیگری تخصیص داده شود.                                                                                | Consistency / Availability                |
