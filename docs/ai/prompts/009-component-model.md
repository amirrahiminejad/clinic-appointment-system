تو یک **معمار نرم‌افزار ارشد** با تخصص در **DDD، معماری لایه‌ای، معماری ماژولار و Event-Driven Architecture** هستی.

من در ادامه Functional Requirementهای یک محصول نرم‌افزاری را به تو می‌دهم.

وظیفه تو این است که فقط بر اساس FRهای ارائه‌شده، **Componentهای منطقی سیستم و ارتباط بین آن‌ها** را استخراج کنی.

### قوانین تحلیل

1. Componentها را از روی مسئولیت‌های کسب‌وکاری و Use Caseها استخراج کن، نه صرفاً از روی Entityهای موجود در متن.
2. Componentها باید دارای **مسئولیت مشخص و مستقل** باشند.
3. از ایجاد Componentهای بیش از حد ریز یا بیش از حد بزرگ خودداری کن.
4. اگر یک قابلیت می‌تواند در یک Component موجود قرار بگیرد، Component جدید ایجاد نکن.
5. ارتباط بین Componentها را مشخص کن و جهت وابستگی را نشان بده.
6. مشخص کن ارتباط‌ها از چه نوعی هستند:

   * Synchronous Request/Response
   * Asynchronous Event
   * Query
   * Command
   * Shared Data / Read Model
7. اگر ارتباطی از طریق Domain Event انجام می‌شود، Event و Publisher و Consumer را مشخص کن.
8. Componentهای مربوط به UI، Database و Infrastructure را فقط در صورتی پیشنهاد بده که از FRها یا نیازمندی‌های استخراج‌شده قابل استنتاج باشند.
9. بین **Business Component** و **Technical Component** تمایز قائل شو.
10. از تبدیل مستقیم هر Entity به یک Component خودداری کن.
11. اگر اطلاعات FR برای تصمیمی کافی نیست، آن را به‌عنوان **فرض یا ابهام** علامت بزن و حدس قطعی نزن.
12. راهکار را تا حد امکان مستقل از تکنولوژی ارائه کن؛ مثلاً به جای Spring Service یا .NET Service از مفهوم Application Component استفاده کن.
13. اگر Microservice مرزبندی مناسبی نیست، صراحتاً اعلام کن و Component/Module را پیشنهاد بده.
14. Componentها باید Cohesion بالا و Coupling پایین داشته باشند.
